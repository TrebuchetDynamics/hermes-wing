# Contributing

The only Desktop product reference is [Nous Research Hermes Desktop](https://github.com/NousResearch/hermes-agent/tree/main/apps/desktop),
locally `hermes-agent/apps/desktop/`. Prior separate-app comparisons are
[withdrawn as official parity evidence](docs/quality/official-desktop-reference.md).
Existing Wing test results do not establish parity with this corrected reference.

Hermes Wing is a Hermes-only Flutter alpha. Keep product language and routes within
the Hermes session/run model described in [CONTEXT.md](CONTEXT.md) and the
[runtime and delivery decision](docs/adr/runtime-and-delivery.md).

## Setup

Use Flutter 3.44.2 and Node.js 22.

```bash
flutter pub get --enforce-lockfile
npm ci
```

Initial Flutter preparation may download the exact public packages already pinned
in `pubspec.lock`. Do not update the dependency manifest, lockfile or checksums to
work around a missing cache. Offline resolution requires these packages to be
cached first; it cannot bootstrap an empty cache.

## Repository map

- `lib/` contains the Flutter client. Hermes API models, transport, and session
  state live under `lib/core/hermes/`; product screens live under `lib/features/`.
- Wing has no host-management service or Go dependency. Use exact advertised Agent
  APIs; missing operations remain unavailable, not compatibility fallbacks.
- `test/` contains Dart unit, widget, and source-contract tests.
- `integration_test/` and `playwright/` cover device and browser flows.
- `docs/` contains setup runbooks, security material, product contracts, and
  architecture decisions.

Most client work can use the deterministic browser fixture without a physical
device. Run `flutter build web --release -t lib/main_e2e.dart` followed by
`npm run web:e2e`. Android speech, acoustic behavior, and platform integration
still need appropriate hardware or an emulator.

## Required checks

Run locked preparation followed by the entire serial Flutter suite:

```bash
flutter pub get --enforce-lockfile && flutter test --no-pub --concurrency=1
```

After successful preparation, the warm-cache offline equivalent is:

```bash
flutter pub get --offline --enforce-lockfile && flutter test --no-pub --concurrency=1
```

Neither command filters the suite or introduces skips. Keep preparation failures
separate from terminal test results; a complete failed suite is not a green check.

These commands do not replace the relevant formatting, analysis, browser,
security or native qualification gates. For full release/cross-boundary work:

```bash
dart format --output=none --set-exit-if-changed lib test integration_test
flutter analyze
flutter test --concurrency=1
flutter build web --release -t lib/main_e2e.dart
npm run web:e2e
npm audit
git diff --check
```

Regenerate the shared README and landing-page visuals after relevant UI changes:

```bash
npx playwright install chromium
npm run readme:assets
```

The generator uses the deterministic Hermes fixture and fails on browser console,
page, or same-origin HTTP errors.

## Where help is useful

The [repository work queue](docs/tasks/work-queue.md) uses `tasks/` through
`autowork tasks`. Do not recreate `TODO.md` or `goals.json`; the archive is frozen
history. Task/plan tooling tests require Python 3.11+ for standard-library TOML.

Follow the [autogoal workflow policy](docs/product/autogoal-workflows.md) for
goal-focused selection, bounded slices, qualification and protected-main integration.

Follow the accepted Android SSH → profiles/multi-session → canonical Bot Chat →
touch-polish priority, preserving Desktop fidelity and existing qualification gates.
Reconcile completed offline work rather than starting duplicate implementations.
Preserve generation, approval/Stop and exact-session restoration without replay. See the
[current goal and qualification boundaries](docs/plans/2026-10-03-desktop-port-goal.md).
Check the
[issue tracker](https://github.com/TrebuchetDynamics/hermes-wing/issues) before
starting larger work, or open a focused issue describing the user problem and
the platform you can test.

Add the smallest regression test that proves non-trivial behavior. Never place
API keys, transcripts, private endpoint URLs, or generated agent state in a
commit. `.pi`, build output, screenshots generated by tests, and local tool
state remain ignored.

## Isolated development and delivery

Use the supported isolated task workspace and keep one writer per workspace.
Preserve unrelated canonical changes. Scoped local task commits are authorized;
independent review and coordinator integration are separate steps. No worker push,
deployment, live operation or protection bypass is authorized by offline work.

Keep each usable outcome's implementation, regression tests and necessary docs
in coherent commits. Run focused checks while iterating and the relevant broader
gates on the frozen delivery candidate. Explicit shipping requests authorize a
normal fast-forward push to `main`, never a protection bypass or force-push.

Archive unmerged history before retiring legacy branch refs. Preserve dirty
files, partial staging and existing QA work; an archive is not integration proof.
Describe the user-visible change, security or privacy impact, platforms tested,
and exact validation commands. Compilation alone does not establish platform
support. Do not claim offline speech, release readiness, or signed distribution
without corresponding runtime evidence.
